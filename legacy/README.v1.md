# sysview

一個指令看完整台機器：**CPU / 記憶體 / GPU / 儲存 / 網路 / 行程**，每一項都能按數字鍵深入。

```
sysview
```

不需要 root，機器上每個使用者都能跑。資料全部直接讀 `/proc` 與 `/sys`。

---

## 目前狀態

| 檔案 | 說明 | 行數 |
|---|---|---|
| `sysview.cpp` | **C++17 正式版**，零外部相依（不用 ncurses） | ~2700 |
| `sysview.py` | Python 3 原型，功能對等，純標準函式庫 | ~2250 |
| `Makefile` / `install.sh` | 編譯與全機器安裝 | |

兩版功能一致，UI 版面相同。C++ 版是要拿去部署的那個；Python 版留著當參考實作跟快速改東西用。

## 安裝

```bash
./install.sh          # 編譯 + sudo 裝到 /usr/local/bin（需要輸入 sudo 密碼）
```

或手動：

```bash
make                  # 只需要 g++，不需要任何 dev 套件
sudo make install     # PREFIX=/usr/local
```

## 操作

| 鍵 | 作用 |
|---|---|
| `1`–`6` | 深入 CPU / 記憶體 / GPU / 儲存 / 網路 / 行程 |
| `` ` `` `~` `0` | 回總覽 |
| `Tab` / `←` `→` | 依序切頁 |
| `空白` | 暫停取樣 |
| `+` `-` | 更新頻率 0.2s ~ 10s |
| `s` `/` | （行程頁）換排序 / 關鍵字篩選 |
| `?` | 說明 |
| `q` | 離開（在深入頁會先回總覽） |

命令列：

```bash
sysview -i 0.5        # 更新間隔
sysview -v gpu        # 直接開某一頁
sysview --snapshot    # 純文字快照後離開，可導向檔案 / 給 watch / cron 用
```

沒有 TTY 時（例如 `sysview > log.txt`）會自動切成快照模式。

## 實測開銷

這台機器：i7-13700（24 執行緒）、62 GB RAM、RTX 4070 Ti、~510 個行程。
在 190×48 的終端機、1 Hz 更新下量測 45–60 秒：

| | 自身 CPU | 常駐記憶體 | 執行檔 |
|---|---|---|---|
| **sysview (C++)** | **0.23 s / 45 s ≈ 0.5% 單核** | **3.6 MB** | **310 KB** |
| sysview (Python) | 0.78 s / 60 s ≈ 1.3% 單核 | 21.2 MB | — |
| htop（對照） | — | — | 277 KB |

換算成整台 24 核機器：**0.02%**。

### 一路上做掉的三個效能問題

1. **掃行程太貴** — 掃全部 `/proc/<pid>/stat` 佔單次取樣 88% 的成本（512 個行程 = 7.2 ms）。
   行程清單不需要跟圖表一樣快，獨立節流成最快 0.75 秒一次；圖表照樣能飆到 5 Hz。
2. **`nvidia-smi` 比整支程式還貴** — 反覆啟動它每次都要重新初始化驅動。
   改成 fork/exec 一個常駐的 `nvidia-smi -l 2`，透過 pipe 讀，成本降到約 1/6。
3. **啟動時的診斷太貴** — `dpkg-query` / `dkms status` / `mokutil` 只有 GPU 壞掉時才有用，
   改成「偵測到 nvidia-smi 失敗才查」。另外 `ip -o addr` 換成 `getifaddrs(3)`，不再 fork。

## 設計決定

**為什麼不用 ncurses** — 這台機器沒裝 `libncurses-dev`，用了就得先 sudo 裝套件。
自己寫 termios + ANSI 反而更輕：畫面是雙緩衝的，每次只把**真的變了的格子**送到終端機
（`Screen::flush()`），比 ncurses 少一層抽象，也完全掌握全形字的處理。

**全形字寬度** — 中文一個字佔 2 個終端格。整份程式的座標計算都走 `dw()`（East Asian
Width），不用 `strlen()`；`Screen::put()` 也會處理「蓋掉別人半個全形字」時的殘留清除。
這是實作過程中真的踩到的 bug —— 一開始用 `len()` 算，框線全部歪掉。

**Intel 內顯使用率** — i915 沒有 `gpu_busy_percent` 這種介面。改用 `power/rc6_residency_ms`
（GPU 進入省電休眠的累計時間）反推：這段期間「沒在睡」的比例 ≈ 忙碌比例。標示為估計值（`使用~`）。
量不到就顯示 `n/a`，不編造數字。

**磁碟使用率跟 `df` 對得上** — 用 `used/(used+avail)`，排除 ext4 保留給 root 的 5%，
而不是 `used/total`。兩者在 915 GB 的碟上差 4 個百分點。

**bind mount 去重** — snap 會把同一個檔案系統掛好幾次，統計數字完全相同，只列第一個。

## GPU 診斷

`nvidia-smi` 掛掉時不會只印一行「失敗」，而是把原因查出來：kernel module 有沒有載入、
`/dev/nvidia*` 在不在、裝了哪些 `nvidia-dkms-*`（多版本並存會打架）、
**DKMS 模組是替哪個核心編的 vs 目前跑的是哪個核心**、Secure Boot 狀態，並附上修復步驟。

> 這台機器一開始就是壞的，診斷直接指出病因：模組只替 `6.8.0-40` 編過，
> 但開機進的是 `6.8.0-90`，而且 `nvidia-dkms-545` 和 `550` 同時裝著。

## 已知限制 / 還沒做

- **每個行程的磁碟 I/O**：`/proc/<pid>/io` 只有自己的行程讀得到，別人的要 root。目前沒做。
- **PCIe / NVLink 頻寬**：`nvidia-smi dmon` 拿得到，但要另一個常駐行程，還沒接。
- **多 GPU**：程式碼有處理，但這台只有一張卡，沒有實機驗證過。
- **AMD 顯卡**：`amdgpu` 的 sysfs 路徑有寫，同樣沒有實機驗證。
- **容器**：沒有 cgroup v2 感知，在容器裡看到的會是宿主機的數字。
- **遠端 / 多機**：沒有。這是單機工具。
- 只在 Ubuntu 22.04 / kernel 6.8 / glibc 上測過。

## 驗證方式

TUI 是在 pty 裡跑起來、用終端機模擬器（pyte）把畫面截下來逐頁檢查的，
八個頁面（總覽 + 六個深入頁 + 說明）零異常，C++ 版與 Python 版版面一致。
